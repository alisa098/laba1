# Лабораторная работа № 1 — Lakehouse и бенчмарк

**Выполнила:** Зуева Алиса Алексеевна  
**Группа:** БИВТ-24-АЭ-2

## Цель работы

Развернуть локальное Lakehouse, выполнить ELT-преобразование данных и сравнить хранение данных с использованием разных алгоритмов сжатия по размеру файлов и времени записи.

## Архитектура

В проекте используются:
- **MinIO** — объектное хранилище.
- **Lakekeeper** — каталог Iceberg.
- **Trino** — выполнение SQL-запросов.
- **PostgreSQL** — служебная база данных.
- **Apache Spark** — обработка данных.

Данные организованы по слоям:
- **Bronze** — исходные данные TPC-H.
- **Silver** — преобразованные данные о возвращённых позициях заказов.
- **Gold** — итоговая агрегированная таблица для аналитики.

## Структура проекта

- `catalog/` — конфигурация каталога и создание warehouse.
- `spark/` — конфигурация Spark.
- `sql/01_validate_results.sql` — проверка схем, таблиц и результатов ELT.
- `sql/02_build_silver.sql` — SQL-запрос для воспроизведения преобразования Bronze → Silver.
- `sql/03_build_gold.sql` — SQL-запрос для воспроизведения агрегации Silver → Gold.
- `sql/04_benchmark_formats.sql` — проверка таблиц и количества строк для сравнения GZIP и ZSTD.
- `ЛР-1__БИВТ-24-АЭ-2_Зуева Алиса Алексеевна__ЛР-1. Бенчмарк. Сравние размера, времяни записи, скорости выполнения агрегаций в Spark.docx` — отчёт по лабораторной работе.

**Примечание:** SQL-файлы `02_build_silver.sql` и `03_build_gold.sql` содержат восстановленные SELECT-запросы для воспроизведения логики преобразований. Они не создают и не перезаписывают существующие таблицы. Файл `04_benchmark_formats.sql` содержит проверочные запросы, а не исходный код измерения времени записи.

## Бенчмарк GZIP и ZSTD

Для сравнения использовались таблицы с одинаковым количеством записей — 6 001 215 строк.

| Алгоритм | Размер данных | Время записи |
|---|---:|---:|
| GZIP | 143,8 MiB | 1788 мс |
| ZSTD | 147,2 MiB | 1035 мс |

В проведённом измерении GZIP обеспечил меньший размер данных, а ZSTD — меньшее время записи. Результаты могут зависеть от порядка выполнения операций и состояния кэша.

## Воспроизводимость ELT

Для повторного выполнения преобразований подготовлены SQL-скрипты:

- `sql/05_create_silver_rebuild.sql` — создаёт отдельную таблицу `lakekeeper.silver.returned_items_rebuild` из данных Bronze. Проверенный результат: 114 705 строк.
- `sql/06_create_gold_rebuild.sql` — создаёт отдельную агрегированную таблицу `lakekeeper.gold.q10_top20_rebuild` из данных Silver. Проверенный результат: 20 строк.

Скрипты выполнены через Trino. Результаты проверены запросами `COUNT(*)` и сравнением первых пяти строк Gold с исходной агрегированной таблицей.

**Важно:** перед повторным запуском необходимо проверить, существуют ли таблицы `returned_items_rebuild` и `q10_top20_rebuild`. Скрипты используют `CREATE TABLE` и не предназначены для повторного выполнения поверх уже созданных таблиц.
